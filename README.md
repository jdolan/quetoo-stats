# quetoo-stats

REST API and database schema for Quetoo gameplay statistics.

## Stack

- **Apache** + **mod_php** (PHP 8.1+, with `mbstring`)
- **MariaDB** (MySQL-compatible)
- **Let's Encrypt** for TLS

## API

### `POST /api/frags`

Accepts a JSON array of frag events from a Quetoo dedicated server.

```json
[
  {
    "level":         "dm_quetoo",
    "attacker":      "PlayerA",
    "attacker_guid": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
    "target":        "PlayerB",
    "target_guid":   "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
    "weapon":        "railgun",
    "mod":           12
  }
]
```

Quetoo v1.0.106 through v1.0.108 post `attackerGuid`, `attackerAi`,
`targetGuid` and `targetAi` instead, because those builds took the JSON key
from the C struct member name and that name had been renamed to camelCase.
Both spellings are accepted, and the camelCase one MUST keep working until no
server in the field runs a build from that window.

Newer Quetoo dedicated servers also send two headers alongside this (and the
`/api/captures`) request, identifying which server instance is reporting:

```
X-Quetoo-Port: 1998
X-Quetoo-Hostname: My Cool Server
```

This lets the stats service unambiguously attribute rows to a specific
server instance (`server_port`/`server_hostname` columns) even when several
instances share one public IP on different ports — something `server_ip`
alone cannot express. Older clients that omit these headers still work; the
service falls back to a live UDP status query keyed by IP alone, which is
only reliable when a given IP hosts a single registered instance.

### `GET /api/stats`

Returns the leaderboard: frags grouped by player, ordered by frags descending.

### `GET /api/stats/<guid>`

Returns one player's kills and deaths, broken down by weapon and by opponent.
`<guid>` is the hashed form, since raw GUIDs are never stored.

### `POST /api/captures`

Accepts a JSON array of CTF capture events, in the same shape as frags.
Captures are read back through `/api/stats`, not through this route.

### `POST /api/sessions`

Accepts one anonymous session record from a Quetoo game **client**, not a
server. The client posts twice per session: at startup with its build and
hardware, and at exit with the duration and map count. Both bodies carry the
same `sessionId`, and the second updates the row the first inserted.

```json
{
  "event":       "start",
  "token":       "b1946ac92492d2347c6235b4d2611184",
  "sessionId":   "3f2504e0-4f89-41d3-9a0c-0305e82c3301",
  "version":     "v1.0.108",
  "build":       "arm64-apple-darwin",
  "buildNumber": "1234",
  "platform":    "macOS",
  "device":      "Apple M3 Max",
  "vendor":      "metal",
  "renderer":    "metal",
  "cpuCores":    10,
  "systemRamMb": 32768
}
```

```json
{
  "event":     "end",
  "token":     "b1946ac92492d2347c6235b4d2611184",
  "sessionId": "3f2504e0-4f89-41d3-9a0c-0305e82c3301",
  "duration":  4210,
  "maps":      3
}
```

`token` is `md5(guid + UTC date)`, computed on the player's machine, so a raw
GUID never reaches this service. It is hashed again here with
`ANALYTICS_SALT`. Because it rotates every day, this table can count distinct
players per day and cannot follow one player across days. Nothing in the
payload identifies a person, a map or a server, and the client address is
neither stored nor logged (see `apache/quetoo-stats.conf`).

Players disable this with `set cl_analyticsUrl 0` in the game console.

Daily active players:

```sql
SELECT date, COUNT(DISTINCT token) AS players FROM sessions GROUP BY date ORDER BY date;
```

Unlike `/api/frags`, this route is unauthenticated - a game client is not a
master-listed server and cannot hold a secret. Field bounds and a per-address
rate limit raise the cost of forged rows without preventing them.

### `GET /api/options`

Returns the distinct server hostnames and map names present in the data, for
the filter dropdowns on the stats page.

Each endpoint file carries its own parameter list in a docblock at the top.
Read `api/stats.php` rather than duplicating it here.

## Setup

```bash
sudo bash install.sh
```

Installs the full LAMP stack, configures MariaDB, deploys the app, and
obtains a Let's Encrypt certificate for `stats.quetoo.org`.

## Configuration

Credentials live in `config.local.php` (generated by `install.sh`, never committed).
`STATS_SALT` and `ANALYTICS_SALT` are defined there too. `install.sh` generates
both on a first install, and leaves an existing `config.local.php` untouched,
because regenerating a salt in use is unrecoverable. The two MUST differ, and
`config.php` refuses to run if they match - see the note in `AGENTS.md`.

## Maintenance

### `maintenance/merge_guid.php`

CLI-only tool (SSH access required, not exposed over HTTP) for merging a
player's frags/captures/matches history from an old GUID onto a new one.
This is the fix for the common case where a player loses their
`quetoo.cfg` (and thus their `guid` cvar), gets a new client-generated
UUID, and their prior stats are orphaned under the old, unused GUID hash —
raw GUIDs are never stored (see `hash_guid()` in `config.php`), so there is
no way to recover the old GUID from the new one; the admin must identify it
by name.

```bash
# Find the orphaned GUID hash by a case-insensitive name substring
# (player names may contain Quake color escapes, e.g. "^1j^9dolan" — search
# a plain substring like "dolan" instead of the decorated name).
php maintenance/merge_guid.php --find=dolan

# Dry run: reports affected row counts per table without writing anything.
php maintenance/merge_guid.php --old=<old-guid-or-hash> --new=<new-guid-or-hash>

# Apply the merge and record it in the guid_merges audit table.
php maintenance/merge_guid.php --old=<old-guid-or-hash> --new=<new-guid-or-hash> \
  --confirm --note="lost quetoo.cfg, verified via discord"
```

`--old`/`--new` each accept a raw client UUID or an already-hashed 64-char
hex value.
